Read Steuerfuesse from the tariff year and implement Basel-Landschaft's formula tariff

Two closed open items and one new refusal reason. Test count rises from 158 to 164.

Steuerfuss vintage: 2024 -> 2026

Scales are imported from 2026 ESTV "Tarife" exports while the Steuerfuesse were
read from the 2024 row of the Steuerfuss workbook. That is not a rounding
difference: applying 2024 multipliers to a 2026 tariff prices a tax regime that
never existed.

  Aargau    1.12 (2024) -> 1.03 (2026)
  Obwalden  3.35 (2024) -> 3.25 (2026)
  Zuerich   0.98 (2024) -> 0.95 (2026)

cantons::SELF_ASSESSMENT_YEAR now names the year, and every workbook-filled
multiplier carries it in its Provenance. Aargau and Zuerich were also
hand-entered in the registry at 1.11 and 0.98 -- values matching neither year's
workbook cell (Aargau's 2024 cell says 1.12). Those overrides are deleted, so the
workbook is the single source and a figure cannot drift from the file it claims
to come from. Obwalden at CHF 100,000 moves 12,978 -> 12,798, Aargau single
14,361.66 -> 13,806.62.

The married Aargau figure exposed a wrong comment as well as a wrong number: the
old text read "2,488 x 2 x 2.07 = 9,869.76", which does not equal 9,869.76. The
simple tax at 50,000 is 2,384, giving 9,488.32 -- and it is deliberately NOT half
the single figure (13,806.62 / 2 = 6,903.31), because two halves at 50,000 cost
less than one whole at 100,000. That gap is the entire point of splitting.

Basel-Landschaft: a tariff published as formulas

BL's export has no band column and no rate column. Each segment is an algebraic
expression giving the simple tax directly, e.g.

  16731  -0.827548* $wert$ + 0.089722* $wert$ * (log $wert$ - 1) + 830.223746

Three decisions, each of which could silently produce a wrong tax:

1. The formulas are stored as SOURCE TEXT and evaluated by
   federal_tax::eval_formula, not transcribed into Rust constants. Transcribing
   is the obvious alternative and it introduces a step where one digit can be
   lost -- in a file whose whole purpose is that numbers trace to a source.

2. Segments are ALTERNATIVES, not increments: the last segment whose threshold
   does not exceed the income supplies the whole tax. That is what makes the
   expressions self-consistent, and the test asserts it -- evaluated at each
   other's thresholds they agree to under 0.001 CHF. A progressive tariff cannot
   jump when a band changes, so that continuity checks the SOURCE DATA.

3. Splitting is NOT applied. BL publishes separate expressions per marital
   status, so the difference is already in the tariff; the married table adds a
   0.49 * $wert$ / 100 relief band from CHF 8,366 that the single table lacks.

Two parser bugs were found and fixed while making this work, both worth naming
because each produced a silent failure rather than an error:

  - `a * b` was parsed as `a`, because the `*` arm called parse_unary and
    discarded the result. Multiplication by nothing is invisible in a formula
    whose leading coefficient happens to be tested alone.
  - `log` was required to be followed by `(`, but the export writes it as a
    space-separated PREFIX operator -- `log $wert$`. Every real BL expression was
    therefore refused.

Neither surfaced until the formulas were actually evaluated; before that, a parse
failure was indistinguishable from "not implemented".

BL is still not priceable, and the reason changed. The Liestal row of the ESTV
Steuerfuss workbook is EMPTY for every year it covers (2024, 2025 and 2026
alike), so BL is blocked on its multiplier, not its tariff.
canton_tax_data(BL).missing_fields() now reports exactly those two multipliers,
and a test pins that -- so supplying a sourced Steuerfuss needs no code change.

Coverage is unchanged at 22 of 26, but the four refusals are now all ONE kind of
missing input (a Steuerfuss cell that is not a plain number) rather than four
different pieces of engineering.

Also fixed while in the area

  - `compare --canton ZH` accepted the flag and priced with Bern's table. It now
    resolves the schedule through the same helper as `optimize`, so the flag
    means the same thing in both commands.
  - The comparison table's breakdown note claimed "official Stadt Bern rates"
    unconditionally, including directly beneath a canton the caller had just
    asked for. It now names the basis actually used.
  - The refusal hint listed Bern as "the one canton with a complete table" and
    said the scale "has not been supplied" for every refusal -- false for the
    four cantons whose scale IS imported. It now names the priced cantons
    (derived, not hard-coded: the count went 3 -> 22 in this repository's life)
    and states only what is genuinely absent.

Documentation

SWISS_TAX_DATA.md records the vintage correction, the four tariff shapes, and BL's
formulas with the three interpretation decisions spelled out. The Aargau worked
example is corrected to 13,806.62 / 9,488.32.

Verified: 164 tests pass, cargo doc --lib clean under -D warnings, clippy at 8
warnings -- no new ones (both new lints introduced here were fixed: an
inconsistent digit grouping and an 8-argument function, the latter by giving
`compare` a parameter struct like `optimize` already had).

Known, not fixed: the repository is not `cargo fmt --check` clean. rustfmt
1.9.0-stable (2026-07-14) reflows ~200 hunks across files untouched here, because
the toolchain is newer than the code was formatted with. Running `cargo fmt`
would bury these changes in a repository-wide reformat, so it is left as its own
change.
