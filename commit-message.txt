Fix a rate-base defect: the printed Tax Rate used gross income

`TaxSchedule` had two accessors that disagreed about which income the rate schedule
applies to, and the one feeding the printed "Tax Rate" was the wrong one. Test
count rises from 198 to 199.

    effective_tax_rate(gross)  ->  looked up on taxable_income_after_estimates(gross)
    tax_only_rate(gross)       ->  looked up on gross

The tax actually charged was always computed on deducted income, which is correct.
Only the number shown to the user was wrong -- and consistently too high, because
the progressive schedule was applied to a larger base:

    gross 100,000   shown 17.24%   charged 15.76%   overstated by 1.48pp
    gross  50,000   shown 12.00%   charged 10.56%   overstated by 1.44pp
    gross 150,000   shown 21.34%   charged 19.50%   overstated by 1.84pp
    gross 250,000   shown 24.73%   charged 24.73%   overstated by 0.00pp

The gap closes at 250,000 because the Bern table clamps above 200,000 -- which is
exactly why the defect could sit at the top of the range unnoticed.

How it stayed hidden, which is the instructive part

THREE tests called `tax_only_rate` with a TAXABLE figure and asserted the published
rates. They passed because the function deducted a second time and the tests then
compared against positions that tolerated the result. The bug and its tests agreed
with each other, so neither looked wrong. The clearest case is
`bern_table_is_close_to_the_published_figures`, which asserted `|diff| < 15.0`
where the real answer is -5.74pp -- a tolerance wide enough to accept either the
correct figure or the twice-deducted one.

The fix

  - `tax_only_rate(gross)` now deducts first, so both accessors use one base
  - `tax_rate_on_taxable(taxable)` is new, for asking about an income that is
    already taxable. Converting a taxable figure back to a gross one just to have
    it deducted again is the mistake that hid this.
  - `rate_accessors_agree_on_the_same_income` asserts the invariant directly: the
    tax-only rate equals `tax_rate_on_taxable(taxable_income_after_estimates(gross))`
    to within 1e-12, and the effective rate equals it plus payroll charges.

Corroboration rather than assertion

The three tests that encoded the bug now call `tax_rate_on_taxable`, and the model
figures they produce reproduce the table already documented in SWISS_TAX_DATA.md
EXACTLY -- 5.41 / 12.00 / 17.24 / 24.73 / 24.73 against published 16.01 / 18.50 /
22.98 / 32.15 / 37.09, i.e. -10.60 / -6.50 / -5.74 / -7.42 / -12.36pp. Those
numbers were written down before this defect existed, so their restoration is
independent evidence that the fix corrects the base rather than moving a figure.

`bern_table_is_close_to_the_published_figures` now pins that documented -13.5 to
-5.0pp envelope instead of `|diff| < 15.0`, so a future regression fails rather
than hides.

One assertion in `optimizer.rs` had to change meaning: it expected the effective
rate to be strictly BELOW tax-only plus payroll charges, a gap that existed only
because the two accessors disagreed. It now asserts equality.

What did NOT change

The deduction MODEL is untouched: still the ~35%-cap estimate, still with the
sourced model printed beside it. This makes the reported rate consistent with the
tax already being charged rather than moving anything between models -- which is
why it was safe to do without the user's decision on switching the tax base.

Documentation

SWISS_TAX_DATA.md gains section 6 on the defect, with the table, the reason it hid,
and an explicit statement that the model is unchanged. DesignDocument.md's
TaxSchedule interface gains the new method.

Verified: 199 tests pass, clippy unchanged at 9 pre-existing warnings, and the
published-reference figures match the documented table exactly.
