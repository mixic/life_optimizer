Import the ESTV deduction tables as data, with their classification

First step of replacing the ~35%-cap deduction estimate in `tax.rs`: the source
data exists and is now imported, typed, and tested. Nothing yet consumes it for a
calculation, so no tax figure changes. Test count rises from 164 to 175.

`src/estv_deductions_data.rs` is generated by `tools/import_estv_deductions.py`
from two ESTV exports for tax year 2025:

  estv_deductions.xlsx         618 rows -> 617 rules, 27 jurisdictions
  estv_deduction_scales.xlsx   466 rows ->  22 phase-out scales

Coverage is complete and even (26 cantons + Bund x the same deduction
categories), so a missing rule shows up as a gap rather than a silent default.

The rule shape is a COMBINATION, not a choice

     deduction = clamp(amount + percent/100 * base, minimum, maximum)

`amount` and `percent` are not alternatives. Aargau's "Pauschalabzug uebrige
Berufskosten" is `Betrag=700, Prozent=10, Maximum=2400` -- 700 plus 10%, capped
at 2400 -- which no single-column model can express. And `Maximum = 0` means the
source states NO ceiling, which is not a ceiling of zero: reading it as one would
zero out most of the table, so `apply` ignores it and the tests pin that.

The rules file also contains non-deductions, which is the trap

The same flat 618-row table mixes three different things:

  Deduction   574  Kinderabzug                                 a real deduction
  Threshold     9  Schwellwert fuer Abzug AHV-/IV-Rentner      a breakpoint
  Other        34  Steuerermassigung pro Kind                  a tax relief
  Other            Maximaler technischer Zinssatz ... FINMA    a rate constant

Summing every row would both double-count and treat a threshold as an amount. So
every row carries a `RuleKind`, the generator prints whatever it could not
classify, and the tests assert the classification is USED, not merely present --
including that the `percent <= 100` sanity bound applies to deductions only,
since the FINMA technical rate is stored in the same column as 350, meaning 3.5%.

Rows that are parts of one rule

Valais's "Pauschalabzug Unterhaltskosten von vermieteten Liegenschaften mit Alter
bis 20 Jahren" appears twice: once as `Prozent=10, Maximum=0` and once as
`Prozent=0, Maximum=15000`. That is ONE rule split across rows. Keeping them
separate means a consumer reads whichever it finds first and silently drops
either the rate or the cap, so the importer merges by (canton, name), taking the
non-zero value of each field, and reports a CONFLICT if two rows disagree -- which
would mean the source is inconsistent, not that row order should decide.

Phase-out scales

The means-tested deductions are step functions of net income that phase DOWN to
zero, so `DeductionScale::amount_at` walks the steps instead of interpolating:

  FR  Abzug fuer bescheidenes Einkommen, Ledige ohne Kind
      4100 at 0, 3900 at 20301, ... 100 at 39301, 0 at 40301

The generated data deliberately selects `Kanton` with `id` excluded: the first run
matched `Kantons-Id` instead and emitted identifiers like `10_SCALE_...` from the
numeric canton id. That is the same trap `import_estv_scales.py` documents, and it
is now pinned by a test asserting every jurisdiction is a real canton code or
`Bund` -- `BUND` was the other first-run output, and nothing else in the codebase
would have matched it.

Status

`tax.rs` still uses the original ~35%-cap estimate, whose components
(commuting = 1.5%, rent = 12%, ...) are invented rather than sourced. Replacing it
is the next step and is deliberately not attempted here: the interesting part is
not the arithmetic but deciding WHICH rules apply to a household. The export lists
every deduction a canton offers and a taxpayer takes a subset, so summing all 574
would be as wrong as the current estimate in the opposite direction. Landing the
data first keeps that decision visible instead of burying it in a large diff.

Documentation

SWISS_TAX_DATA.md gains a Deductions section recording the two tables, the
combination rule shape, the three rule kinds with their row counts, the merged
Valais rule, and the phase-out scales -- including an explicit statement that the
figures are imported but not yet applied, so no reader mistakes this for a
completed deduction model. The `--canton` section is corrected: it still described
Bern as "the one canton with a complete table" and printed the old error message.

Verified: 175 tests pass, clippy at 9 warnings -- the same pre-existing set as
HEAD, no new ones (the percentage bound was scoped to deductions after it
correctly rejected the FINMA rate constant).
