Add conversion-rate transparency, consumption tiers, and achievement constraint

Implements FutureWork.md §10 (conversion-rate transparency), §5.1
(elasticity-tiered consumption), and §5.2 (employer achievement capacity),
and fixes four defects found while doing so. Test count rises from 36 to 91.

Feature: conversion rate (FutureWork §10)

monte_carlo.rs gains ConversionRateScenario (Statutory/FundTypical/
FutureProjection/Custom), PensionRange, PensionFundProfile, and a shared
effective_conversion_rate() used by both the optimizer's security-utility
term and the Monte Carlo projection, so the two engines can no longer
disagree on which Umwandlungssatz is assumed. Deferred retirement scales
whatever base rate applies, since annuitising over fewer expected years
raises the rate independently of the base.

simulate_conversion_rate_uncertainty() draws the rate from a distribution
centred on the projection, truncated to [5.0%, 6.8%], and reports
percentiles plus CVaR over the worst decile. Truncation compresses both
tails, which pulls CVaR toward P10; the CLI says so explicitly rather than
letting the reader assume the two are independent. The band (1.0pp) is an
explicit assumption, not a fitted dispersion, and is labelled as such.

PENSION_FUND_PROFILES provides reference rates (publica, bvk, statutory,
typical). Each entry names its provenance, and the CLI prints a
verification reminder whenever a profile is used, because a stale rate is
a plausible-looking wrong input. --conversion-rate takes precedence.

New flags: --conversion-rate, --pension-fund. Pension range is now
standard output.

Feature: elasticity-tiered consumption (FutureWork §5.1)

New consumption.rs implements the sparing model from THEORY_OF_SPARING.md
§7c/§8: inelastic, quasi-inelastic and elastic tiers, with the elastic
tier priced at profile * sparing discount * utilisation penalty. Tiers are
derived from the existing basket rather than replacing its fields, per
§8's own instruction ("a multiplier ... applied to the existing
discretionary field"), which keeps existing callers working and avoids
duplicating quantities that would have to be kept consistent.
tiers_partition_the_basket_exactly asserts the tiers sum to the full basket
with nothing double-counted.

Feasibility now tests the mandatory floor (inelastic + quasi-inelastic)
rather than the full basket. The previous behaviour treated the savings
goal and discretionary spending as unavoidable, which made §3.1's claim --
the same work percentage being feasible under one lifestyle and infeasible
under another -- false in code, and reported CHF 120k with two children as
having no affordable option at all.

New flags: --consumption-profile, --sparing-ratio,
--utilization-discipline, --quasi-inelastic-share.

Feature: employer achievement constraint (FutureWork §5.2)

AchievementConstraint implements A = H*P*(1+alpha) >= G. A candidate is now
feasible only if it is both affordable and deliverable. Adds the two
derived answers the critique asks for (§1.2, §3a): the lowest viable work
percentage, and the AI gain needed to justify a given reduction. When even
full-time work cannot reach the goal the model returns no viable percentage
rather than a number, and infeasible searches distinguish Unaffordable from
AchievementUnreachable, because the remedies differ entirely.

New flags: --required-output-index, --ai-productivity-gain.

Fixes

- AHV double-count: run() baked ahv into monthly_pensions and added it again
  for median_total_monthly, while run_regime_switching excluded it. All
  three simulation paths now hold BVG only in the pension arrays, add AHV
  exactly once for the *_total_monthly figures, and use total income for
  the adequacy and quality-of-life comparisons. The BVG-only table is
  labelled as such so a reader cannot mistake it for total income.
- u32 underflow panic at optimizer.rs:195 for anyone at or past retirement
  age. validate_ages() now rejects the input with a clear message and exit
  code 2 instead of a backtrace.
- False optimum: the tool announced "OPTIMAL SOLUTION FOUND" directly above
  "BELOW REQUIREMENTS", and when nothing was affordable it ranked candidates
  by utility -- which favours deep under-employment, because leisure and
  health scores rise as income falls. The fallback now minimises the
  shortfall, and the headline reflects which constraint actually failed.
- TOTAL UTILITY printed "7." instead of "7.00": a {:.2} specifier applied to
  a String, which Rust silently ignores.

Also fixes a calibration bug found during implementation: the utilisation
penalty was normalised against an arbitrary baseline, so a household
declaring no sparing still had discretionary spending inflated ~54%, making
it look less affordable than the basket it was compared against. It is now
normalised so full discipline yields exactly 1.0;
neutral_configuration_has_unit_multiplier guards the regression.

Infrastructure

Adds src/lib.rs so tests/ can import the crate -- a binary-only crate cannot
be imported by integration tests, which is why the suite was previously
confined to src/. main.rs becomes a thin CLI wrapper over the library and
contains no domain logic. run_optimization takes an OptimizeParams struct
rather than seventeen positional arguments.

Tests move to tests/ (conversion_rate, optimizer_behavior, cli,
consumption_model, achievement_constraint, cli_consumption_achievement,
pension_fund_and_stochastic); the six unit tests that need private access
stay in src/. cli.rs drives the compiled binary, which is the only way to
test exit codes and user-facing text.

Adds .github/workflows/ci.yml running fmt, clippy and the full suite on
Linux and Windows.

Docs

FutureWork.md status tables and §5.4/§10.9/§10.10 record what shipped and
where the implementation deliberately diverged from the sketch.
MATHEMATICS.md gains §3.1.1 (tiers and sparing multiplier), §6.2.1-6.2.2
(conversion scenarios, projection, stochastic rate) and §14.1.1 (the
achievement constraint and its two derived quantities). EXAMPLES.md gains
worked examples, all verified against actual output.

Corrects two numeric errors in FutureWork.md §10 itself: the §10.3 table
listed 5.00% for 2050 where the formula gives 5.86% (the floor binds in
2074), and the §10.4 example printed CHF 5'374 at the statutory rate, which
implies ~CHF 948k rather than the CHF 500k the section describes.
projection_matches_documented_table now checks the published table against
the code, so the document cannot silently drift from the model again.

Not done, deliberately

- §4.1 calibration of the regime transition matrix and return parameters.
  Ranked first in FutureWork §6, but it needs historical Swiss BVG and
  business-cycle data that this repository does not contain. An uncalibrated
  model with more parameters is not an improvement, so §4.2-4.3 (copula,
  jump-diffusion) were not started ahead of it.
- Historical conversion-rate analysis and a community fund database: both
  need external data and, for the database, an ongoing maintenance model.
- Capital-withdrawal optimisation (lump sum vs annuity and its tax
  treatment): separate modelling work.
- The conversion-rate uncertainty band is an assumption. Fitting it from
  observed fund rates is the same calibration work as §4.1.

Verified: 91 tests pass across 9 targets, cargo doc --lib clean under
-D warnings, no new clippy warnings (8 pre-existing remain).
